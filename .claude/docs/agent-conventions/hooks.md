# Fleet hooks and scripts

Contract C7 (2026-10-20). Rules that used to live only in prose are enforced by Claude Code hooks in `hooks/` (linked to `.claude/hooks`) and run by scripts in `fleet/scripts/` and `scripts/`. Every hook fails open on its own error and blocks (exit 2, message saying how to comply) only on a deliberate rule violation. Kill switch for all hooks: start Claude with `FLEET_HOOKS=off`.

## How hooks run (verified 2026-10-20, Claude Code 2.1.305, Windows 11)

- Hook commands run in **Git Bash** (`$0` = `/usr/bin/bash`), not cmd or PowerShell. `$HOME` and `$CLAUDE_PROJECT_DIR` expand; MSYS converts `/c/...` arguments, so `node ".claude/hooks/x.js"` works on Windows and Linux alike.
- `PreToolUse` exit 2 blocks the call and feeds stderr to the model, which then reports or fixes it. Main-session payloads have no `agent_id`; calls made **inside a subagent** carry `agent_id` and `agent_type` (the PM's own `Agent` dispatches arrive with `agent_type: "project-manager"`).
- `Agent` `PostToolUse`: a foreground agent's `tool_response` carries `agentId`, `resolvedModel`, `totalTokens`, `totalToolUseCount`, `totalDurationMs`. A background agent (also the default when `run_in_background` is unset) returns only a launch receipt (`status: "async_launched"`, `agentId`, `outputFile`). No hook ever sees the task-notification usage line.
- `SubagentStop` carries `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message`, `stop_hook_active`, no usage and no description. The sidecar `<session>/subagents/agent-<id>.meta.json` holds `description`, `agentType`, `toolUseId`, `finished`. Foreground order: `SubagentStop` fires before the `Agent` `PostToolUse`.
- `totalTokens` equals the last API turn's input + cache-creation + cache-read + output tokens of the subagent transcript, and `totalToolUseCount` its distinct `tool_use` blocks; the ledger hook computes the same from the transcript for background agents.
- `Stop` carries `stop_hook_active` and `background_tasks`; it fires at every main-turn end (also after a background notification). Exit 2 from `Stop`/`SubagentStop` makes the agent continue once; the second stop has `stop_hook_active: true`.
- Matchers are tool names: `Agent`, `Bash`, `ArtifactData` (a deferred tool, matched by its plain name), MCP tools as `mcp__<server>__<tool>` (payload adds `mcp_server`). `ArtifactData` is absent in `claude -p` sessions, so the decision-card hook was tested through unit tests and the documented tool schema only.

### Per-project sessions

When `$CLAUDE_PROJECT_DIR/.claude/project.json` exists (written by `scripts/sync-project-definitions.js`), the session is that project's PM and the hooks need no fleet-state or registry: slug and path come from `project.json` (registry lookup is the fallback for other slugs); the dispatch gate treats the session as fleet context, so the main session's own `Agent` calls need `[<slug>/<TASK>]` and any other slug is blocked; `ledger-usage.js` writes every hook line (usage, project-manager dispatches included, and QA's `red_confirmed`) to `$CLAUDE_PROJECT_DIR/.project/ledger.pending.jsonl` (`projectContext().pending`; the sync's `fleet:managed` block ignores `.project/ledger.pending.jsonl*`, the claimed `.flushing` copy included), and the dedupe and the dispatch gate read it (and the claimed copy) before `ledger.jsonl`; at `Stop`, `stop-checks.js` never counts either file as dirt, flushes it into `ledger.jsonl` once its oldest line is `FLEET_LEDGER_FLUSH_MIN` minutes old (default 45), and writes the session's own line (to the pending file) first (`agent: project-manager`, `task: ritual`, `agent_id: session-<id>`, `cumulative: true`, from the session transcript, when `.project/` is dirty, a flush is due, or the session dispatched fleet agents and has no line yet; each line is the session's whole context so far, so audit-rollup counts the last per `(run_id, agent_id)`, never a sum, and a later run of the same session as the growth since the previous run), then blocks once per distinct uncommitted `.project/` state instead of checking fleet-state, except when the only change is hook lines appended to `.project/ledger.jsonl` while a background agent this session launched is still running (committed at wrap-up; with nothing outstanding the Stop may be the last, so it blocks). So the uncommitted-`.project/` block fires about once per 45 minutes plus at WRAP UP (which runs `--flush` first); lines still pending when a container is discarded without WRAP UP are lost, at most about 45 minutes of them; `decision-card-validate.js` also accepts `recorded_by: "<slug> PM"` for a main-session chat decision. The vendored copies are registered in the project's `.claude/settings.json` as `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<name>.js`. Agent worktrees live under `.claude/worktrees/`, which the same `.gitignore` block ignores (the platform's own stop hook flags them as untracked otherwise). Commit statuses and check runs return 403 in the cloud, so reviewers and the verifier rely on the local suites and the sign-off record, never a status. Without `project.json` nothing changes. On a workstation with the user-level hooks installed both copies run; their blocks agree and the ledger write is de-duplicated per `agent_id`.

### Gate events (session audit, 2026-10-22)

Every block by `agent-dispatch-gate.js`, `git-guard.js` (merge gate included), `stop-checks.js` and `decision-card-validate.js` appends one line: `{ts, run_id, project, task, agent, outcome: "gate_block", source: "hook", hook, reason, session_id}`. Each hook's `decide()` returns `{block, gate: {reason, ...}}`, and `runHook` writes the line through `recordGateBlock` in `hooks/lib/common.js`. The write is best effort: a failure (an unwritable file, for example) is swallowed, and the exit code and message stay the same. Allows write nothing. The write reads only the dispatch record file and adds no git calls.

- `run_id`: derived the way the ledger hook does it. The subagent's parent dispatch `Run id:` comes first, then the session's last dispatch that carried one, else `session-<date>-<sid8>`.
- `task`: the dispatch tag when the block is about one, else the subagent's dispatch record, else `adhoc`.
- `agent`: the hook's subject, which is the dispatched type for the dispatch gate. Otherwise it is the subagent's `agent_type`; the main session of a per-project session is `project-manager`; otherwise `null`.
- **Target.** In a per-project session the line goes to `.project/ledger.pending.jsonl`, like usage lines, and is flushed with them. In fleet mode it goes where `ledger-usage.js` would put a usage line for the same subject (fleet-state `ledger.jsonl` for `fleet/` and project-manager, else the project's `.project/ledger.jsonl`), but only when the project is known from the tag or the subagent's dispatch record. A coordinator main-session block, and an untagged block with no dispatch record, has no clear project ledger, so it is not logged. `stop-checks.js` logs only in per-project sessions (`projectOnly`): in fleet mode the line would dirty the very file its block is about, and the next Stop would block again.
- `stop-checks.js` treats appended `gate_block` hook lines like usage and `red_confirmed` lines (no block while background agents run). `audit-rollup.js --validate` accepts the lines, rejecting an unknown key, an unknown `reason`, or a reason paired with another `hook`. They are left out of every DM-12 aggregate. The JSON adds `ledger_summary.gate_blocks` `{count, by_hook, by_reason}` and the status block adds a fifth line `gate_blocks <n> <hook>/<reason>=<n> ...`, both only when the current run has gate lines, so the FR-18.3(f)/(g) shape holds otherwise. Session audit: `session-audit.md`.

## Install, uninstall, cloud

- Install (coordinator, after review): `node scripts/install-links.js --hooks --dry-run`, then without `--dry-run`. It links `.claude/hooks`, backs up `settings.json` to `settings.json.bak-<timestamp>`, and adds each fragment hook to the same event and matcher unless that exact command is present. Re-running changes nothing.
- Uninstall: `node scripts/install-links.js --remove-hooks` removes exactly the fragment's commands; `FLEET_HOOKS=off` disables them without editing settings.
- Never test install-links with only `--home`: without `--no-state` it would also re-point `<fleet-state>/scripts`, so the script refuses `--home` without `--no-state` or an explicit `--state`. Tests use `--home <tmp> --no-state`. Run the real install from the main claude checkout: the script refuses to link the real `~/.claude` to a linked worktree unless `--allow-worktree` is passed.
- `hooks/settings.fragment.json` is a valid `settings.json` on its own, so it doubles as a repo-level `.claude/settings.json` for a single-repo cloud session. Commands use `.claude/hooks/<name>.js`, which `scripts/cloud-setup.sh` creates through install-links, and are guarded with `[ ! -f "$f" ] || node "$f"`, so a session without the claude repo attached runs no hooks instead of erroring. Env overrides for tests: `FLEET_STATE`, `FLEET_HOOKS_STATE`, `CLAUDE_HOME`, `FLEET_REPOS_ROOT`; `FLEET_LEDGER_FLUSH_MIN` sets the pending-file flush age (minutes).
- Tests: `node --test hooks/test/*.test.js fleet/scripts/*.test.js scripts/test/*.test.js`.
- Per-project vendoring: `node scripts/sync-project-definitions.js <project> [--slug s] [--aws-profiles file] [--aws-profile name]... [--aws-default name] [--batch-minutes n] [--dry-run] [--check]` (see `docs/cloud-environment.md`, Per-project sessions).
