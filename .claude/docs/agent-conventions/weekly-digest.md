# Weekly Digest — Stakeholder Status

Applies to every project. Defines the **weekly digest** artifact that the PM generates at every sprint checkpoint, for handoff to a coworker, stakeholder, or exec audience to compile into a formal status report.

This is **distinct** from `.project/project-status.md` (always-current snapshot), the PPTX status report (formal milestone deck), and the page's weekly `fyi` digest card of auto-resolved items ([[autonomy-bar]]), which is for the owner, not stakeholders. The digest is plain-language, outcome-framed, weekly, and stakeholder-audience.

## When to generate

- At every sprint checkpoint (weekly, per [[sprint-cadence]])
- On-demand if a stakeholder asks for an interim digest mid-sprint

## File location

`.project/sprints/digest-YYYY-MM-DD.md` — date-stamped, never overwritten. The date is the sprint-end date — get it deterministically from `python .claude/scripts/lib/dates.py` (`.data.week_ending_fri`, or `--week-ending <day>` for a different sprint-end weekday). The "Open critical bugs" / sprint-outcome counts in the Health snapshot come from `python .claude/scripts/lib/project_artifacts.py count .project/TODO.md`.

`.project/sprints/` is owned by the PM. Add to `.gitignore` if the project does not want digests in version control (default: track them).

## Audience and voice

Audience:
- A coworker who will paste this into a stakeholder report template
- A non-engineer reading the report (exec, business owner, customer-facing partner)

Voice:
- **Outcome language**, not commit language. "Customers can now reset their own password" — not "merged PR #47."
- **No jargon**. No PR numbers, no SHA references, no internal task IDs, no engineering vocab unless the audience uses it.
- **Honest framing**. If something slipped, say it slipped. If a risk is real, state it.
- **Short**. The whole digest should fit on one screen.

## Template

Copy below the `---` into a fresh `digest-YYYY-MM-DD.md`.

---

```markdown
# Weekly Status — [Project Name] — Week ending [date]

## TL;DR

[2–3 sentences. The headline of the week. If a stakeholder reads only this paragraph, what do they need to know.]

## Shipped this week

[User/business-visible outcomes. Each bullet should make sense to someone who didn't sit in a standup. Skip purely internal changes (refactors, infra, tests) unless they have a visible knock-on effect.]

- [Outcome]

## In flight

[Active work + honest ETA framed as confidence, not date. Better: "On track for next week" / "At risk for next week — see Risks" / "Pushed out — see Risks". Avoid false precision.]

- [Item] — [confidence framing]

## Blockers visible to stakeholders

[Only blockers a non-engineer should know about: waiting on decisions, third parties, budget, vendor access, legal review. Internal engineering blockers stay out of here — those are PM-owned and shouldn't surface as stakeholder concerns.]

- [Blocker] — needs: [decision / approval / access from whom]

## Risks

[Things that might affect timeline, scope, cost, or quality. Plain language. Each risk has a likelihood word (low/medium/high) and what's being done about it.]

- [Risk] — likelihood: [low/medium/high]. Mitigation: [what we're doing].

## Coming next week

[The top 1–3 things committed to next sprint (pulled from backlog). Phrase as outcomes.]

- [Outcome]

## Health snapshot

| Metric | Value |
|---|---|
| Sprint outcome | Shipped [X] of [Y] committed |
| Cost trajectory vs prior week | ON / OVER / UNDER budget |
| Open critical bugs | [N] |
| Open P0/P1 security findings | [N] |
| Live environments | [list — dev, staging, prod with status] |

## Links

- Latest dev deploy: [version + date]
- Latest staging deploy: [version + date]
- Latest prod deploy: [version + date, or "Not yet LIVE"]
- Live URL: [if relevant]
- Dashboards: [if relevant]

---

> Generated by Project Manager from `.project/project-status.md`, `.project/sprints/sprint-NN.md`, `.project/deployment-log.md`, and `project-status/cost-summary.md`. For internal engineering detail, see those source files.
```

---

## Source artifacts the PM reads to compile the digest

| Source | Used for |
|---|---|
| `.project/project-status.md` | TL;DR, In flight, Blockers, Risks |
| `.project/sprints/sprint-NN.md` (current sprint, closing) | Shipped, Sprint outcome metric |
| `.project/sprints/sprint-(NN+1).md` (next sprint, planning) | Coming next week |
| `.project/deployment-log.md` | Live environments table, links |
| `project-status/cost-summary.md` | Cost trajectory metric |
| Project's `.project/decisions.md` | Any stakeholder-relevant decision made this sprint |
| Project's `lessons-learned.md` | Only if a lesson is stakeholder-relevant (rare) |

## Voice checklist before delivering

- [ ] No PR numbers, SHAs, or task IDs
- [ ] No engineering jargon (CI, ORM, refactor, migration, ECS, etc.) unless the audience uses it
- [ ] Every "Shipped" item is phrased as a user outcome, not a code change
- [ ] Every "In flight" item has a confidence word, not a date
- [ ] Every "Blocker" is one a non-engineer needs to act on
- [ ] Every "Risk" has a mitigation
- [ ] Fits on one screen when rendered

## Delivery

After generating, PM tells the human:

> "Weekly digest generated: `.project/sprints/digest-YYYY-MM-DD.md`. Ready for handoff to [coworker]."

Do not auto-share, post, or email the digest. The human decides who sees it and when.

## Why this exists

Pre-rule behavior: stakeholder status was either ad-hoc (the PM verbally summarized when asked) or buried in the PPTX format that's overkill for weekly cadence. Coworkers building external reports had to translate from engineering language each week. This format pre-translates once, weekly, and makes handoff a copy-paste.
